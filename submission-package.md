# Prepare my submission

When the analyst asks for submission items, a handoff, or a submission ZIP, use the existing project work. Do not restart Grill or the build.

1. Locate the current editable three-slide presentation, recorded team app link/version, and project log. Use [presentation-deliverable.md](presentation-deliverable.md) and [project-log-guidance.md](project-log-guidance.md). If the presentation or log is missing, prepare it from the available evidence using the referenced guidance. Do not package an empty template as completed work. Ask only for missing information that cannot be recovered from the project; mark unrecorded timing and unverified work honestly. The skill cannot infer the analysts' private thought process: record their expressed decisions and reflections.
2. Reconcile the selected presentation, app version and log. Confirm the editable deck contains written Q1–Q6 answers on its last slide. Summarize any unfinished features or untested requirements. Ask the team to review the answers and log; preparing a ZIP does not attest to their review or authorize an upload.
3. Prepare a reviewed project snapshot, not just the deck. Include the team's current frontend, all server job sources, local prototype, project instructions, decisions and test evidence safe for app-wide sharing, dependency manifests/lockfiles, assets, and synthetic or kit-permitted public data needed to reproduce the demo. Use the current Vibes build skill to pull the team's actual deployed frontend and job scripts to a separate snapshot folder; retain local changes and label any differences from the version demonstrated. Do not overwrite work or deploy changes during packaging. Capture non-secret app configuration (library names, job settings, connector identifiers), app/version IDs and retrieval time. Do not export live records/documents indiscriminately; use only explicitly permitted synthetic/public fixtures. If source retrieval fails, include the available local source and clearly label the snapshot incomplete.

   Write `REBUILD.md` with the app link/version, file map, local run/build commands, deployment/setup steps, required connectors and secret **names only**, data seeding steps, tests actually run, and omissions. Explain that Vibes services, permissions, credentials and live data are not embedded in the ZIP and must be reconfigured. A source snapshot is not a standalone offline Vibes app. Do not claim restoration works unless tested.

   Create a JSON array of explicitly reviewed relative file paths (use `/` separators), including `REBUILD.md`, for the helper's `--project-files` argument. Review the selected file contents, not just names, for secrets and private data. Keep the confidential feedback log OUT of the project snapshot; it is packaged separately and stored behind team/admin checks. Decks and project archives use app-scoped document storage. Include safe technical evidence, but exclude sensitive personal reflections, private client information, raw chats, account configuration, caches and Git history. Record exclusions in `REBUILD.md` without copying their contents. The helper's automatic checks supplement, not replace, this review.

4. Run the supplied [packaging helper](../scripts/prepare-submission.py) using the available Python interpreter. From the kit folder:

   `python scripts/prepare-submission.py --presentation "path/to/deck.pptx" --log "path/to/completed-log.md" --app-url "https://www.chathamvibes.com/vibe_apps/TEAM_APP_ID" --app-version "recorded version" --project-root "path/to/reviewed-snapshot" --project-files "path/to/reviewed-file-list.json" --output-root submission`

   Replace the arguments with observed paths and the actual team app. Use `not recorded` only when the version is genuinely unavailable, not a guess. The helper reads this kit's project key from its manifest and creates a uniquely dated folder and ZIP inside `submission/`, preserving earlier packages. Do not ZIP the whole project or recompress the helper's ZIP. It uses a deliberately simple format supported by the hub. If Python is unavailable, retain the individual files and explain the fallback; do not silently install tools.
5. Check the ZIP and show the analyst clickable absolute links to the ZIP and its files, a short contents checklist, the app link/version, and any remaining gaps. Do not call the package complete if required items are missing. Never include credentials, environment files, chat exports, internal demos, node_modules, or unrelated project files. The helper packages `presentation.pptx`, `project-log.md`, `submission.json` (app link/version), `README.txt` (upload instructions), and `project-archive.zip` (the reviewed project snapshot with a generated SHA-256 file inventory). The deck and project archive each have a 50 MiB upload limit. The generated outer ZIP can be up to 101 MiB.
6. Tell the analyst: open your assigned project in the hub after teams are finalized, save the same app link, choose **Load submission ZIP**, review the loaded items, confirm review, then click **Submit team package**. The ZIP is read locally; the presentation, source archive and log are saved separately. The whole ZIP is never stored as a shared document. Keep the receipt. Individual-file upload remains available. Email the ZIP only if needed and only to the facilitator address supplied by the organizer; do not email or submit automatically.

Suggested analyst request: **“Prepare my full project submission ZIP, including the app source and rebuild instructions, presentation, app link/version, and project log/feedback. Flag anything missing and show me the files to review.”**
